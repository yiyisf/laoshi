# 摸高沙箱摸底（为数字工程师挑战赛）

赛题：在摸高平台上提交 **skill 或专家**（多个 skill 组合的能力）。laoshi 本身就是一组 skill（`/laoshi` 入口、手册、方法、原则）加一个确定性的流水线引擎，天然是一个"专家"。摸底要回答的是：**这个专家在摸高上能以哪种形态工作**。

| 形态 | 需要平台允许 | 流程保证 |
| --- | --- | --- |
| 甲：专家 + 后台引擎（模式 A） | skill 能执行 shell 和 node；后台进程在对话结束后还活着；有命令行能起任务、查状态 | 最强：步骤、轮次、质量门都由引擎保证 |
| 乙：专家在对话里编排（模式 B） | skill 能执行 shell 和 node；对话里的 agent 能起子 agent | 较强：顺序和结果校验由 `laoshi` 命令保证，推进靠对话 agent |
| 丙：只有 skill（纯提示词） | 只要能上传 skill | 弱：只有访谈、需求说明、验收清单这些方法 skill，没有引擎 |

## 一、自动部分（约 10 分钟）

在摸高的对话里（或沙箱终端里），把 `probe.sh` 放到 `/data/workspace` 下运行：

```bash
bash /data/workspace/probe.sh            # 知道平台命令行的名字时：bash probe.sh <名字>
```

它会收集系统和工具、环境变量**名字**（不记值）、进程链（看出对话背后是哪种 agent）、skill 文件和目录在哪里、npm 源能否安装、外网能否连通、平台命令行的帮助，并起一个存活测试的后台进程。结果在 `/data/workspace/laoshi-probe/laoshi-probe-out.tar.gz`。

然后**结束这次对话**，5 分钟后和 30 分钟后各在**新对话**里运行一次：

```bash
bash /data/workspace/probe.sh --check
```

分享前请打开 `out/` 下的文件过一遍：脚本已经尽量脱敏，但内部地址、项目名之类请按公司要求再处理。

## 二、手工部分（约 1 小时）

每个实验把**你做了什么、平台的界面或输出原样是什么**记下来（截图或文字都可以）。

### S1 skill 和专家的格式

1. 平台上 skill 是什么格式：一个 `SKILL.md`（带 `name`、`description` 头）？还是平台表单？能不能**带附加文件**（脚本、模板、子目录）？大小和文件类型有没有限制？
2. 专家怎么组合 skill：列表勾选？一份说明里引用？专家自己有没有"系统提示词"？
3. 新建一个最小 skill，内容只有一句：`被调用时，运行 pwd 和 ls -la "$SKILL_DIR"（如果没有这个变量就运行 env | grep -i skill），把输出原样告诉我。` 在对话里触发它。记录：**怎么触发**（斜杠命令、点名、自动）；**skill 的文件在运行时位于哪个目录**；附加文件能不能读到。
4. 一个 skill 里写"接下来使用另一个 skill X"，看对话 agent 会不会加载 X。

### S2 对话 agent 的能力

在一个挂了上面 skill 的对话里依次让它做：

1. `运行 node -v 和 git --version。`
2. `在 /data/workspace/s2 下 git init 一个仓库，写一个文件并提交。`
3. `起一个子 agent（如果你有这种工具），让它在 /data/workspace/s2 下创建 sub.txt。` 记录有没有子 agent 工具、叫什么、子 agent 能不能执行命令、主对话能不能等它做完拿到结果。
4. `运行一个需要 3 分钟的命令：sleep 180; echo done。` 记录会不会超时被打断、单条命令的时间上限。
5. `在后台运行 nohup bash -c 'sleep 600; echo ok > /data/workspace/s2/bg.txt' &，然后结束本轮回答。` 10 分钟后看 `bg.txt` 有没有出现。

### S3 平台命令行（如果对话或沙箱里能用）

按 [平台摸底清单](../../design/platform-discovery.md) 的实验 1（起一个最简单的任务、反复查状态）和实验 2（HITL：提问、恢复、取消）做。这两项决定能不能做形态甲。

### S4 比赛规则（问组织方）

1. 评审怎么试用提交的专家：用自己的项目，还是给定的样例？在谁的沙箱里？
2. 专家能不能依赖**第一次使用时安装**的东西（比如从内网 npm 镜像装 laoshi），还是必须自带全部文件？
3. 有没有时间、token、费用上限？一个需求跑几个小时是否可以接受？
4. 提交物除了专家本身，要不要说明文档、演示视频、效果数据？

## 交付

把 `laoshi-probe-out.tar.gz`、两次 `--check` 的输出、S1～S4 的记录发回来。我据此写摸底报告（`docs/discovery/mogao/report.md`），定专家的形态，然后开始做。

## 第二轮（第一轮结果见 [report.md](report.md)）

第一轮确认了后台进程活不过一次执行，所以要看平台命令行 `aimax` 能不能"在一次执行内起一个 agent 并等它做完"。

1. 把 [probe2.sh](probe2.sh) 放到 `/data/workspace` 下运行：`bash /data/workspace/probe2.sh`（约 3 分钟）。它收集 `aimax` 每个子命令的帮助、`/aimax/extensions` 下 skill 的开头，并从内网镜像试装 `@yiyi_zhang/laoshi`、运行一次。最后一项会 `sleep 75`，用来看超过 60 秒的命令对话会不会等它结束。
2. 看完帮助后，按帮助里的写法用 `aimax run` 起一个最小任务（提示词："在当前目录创建文件 hello.txt，内容为 ok，然后结束"），记录：完整命令行；是阻塞到结束还是立即返回；返回什么（任务 ID、输出格式）；`hello.txt` 出现在哪个目录；有没有查状态、取消的命令；能否指定工作目录、模型、提示词文件。
3. 在对话里问 agent：`你有没有起子 agent（子任务）的工具？叫什么？` 有的话让它起一个子 agent 创建 sub.txt，记录主对话能否等它做完、拿到结果。
4. 在对话里让 agent 运行 `sleep 600; date`，记录：对话是否一直等到结束；有没有总时限（超时后返回什么）。
5. 问组织方或看平台文档：专家怎么定义和提交（能否带脚本等附加文件）；评审在谁的沙箱里试用；是否允许第一次使用时从内网镜像安装依赖。

把 `laoshi-probe-out2.tar.gz` 和第 2～5 项的记录发回来（同样先脱敏）。
