# laoshi 作为摸高上的"专家"

- 状态：草案。依据是[摸高沙箱摸底第一轮](../discovery/mogao/report.md)；标为"待确认"的地方要等第二轮结果。
- 背景：摸高的数字工程师挑战赛，赛题是在平台中提交 skill 或专家（多个 skill 的组合）。laoshi 本身就是一组 skill（`/laoshi` 入口、手册、方法、原则）加一个确定性的流水线引擎，天然是一个专家。

## 1. 约束（来自摸底）

| 约束 | 对 laoshi 的影响 |
| --- | --- |
| 每条命令执行完，沙箱就被回收；后台进程活不过一次执行 | 引擎不能常驻后台。每次调用都要从状态文件读起、做完一段、写回状态再退出 |
| 只有 `/data/workspace` 持久 | 安装根、程序、需求状态都放在工作区：`LAOSHI_HOME=/data/workspace/.laoshi`；`$HOME` 每次重置，所以每条命令都要带上这个变量 |
| 一次执行内可以跑长任务，可以用 `aimax run` 起任务并等它结束 | 一步（方案、实现、评审……）可以在一次执行内做完 |
| 没有定时、没有向对话推送消息的方式（待确认） | 进展只能作为每次命令的输出回到对话；"预约开始""自动继续"降级为"告诉使用者下一步说什么" |
| npm 走内网镜像，公网不通 | 第一次使用时从镜像安装 `@yiyi_zhang/laoshi`（固定版本）；模型只能用平台的（`AIMAX_MODEL`） |
| 没有 mvn、gradle | Java 项目的构建和测试在沙箱里跑不了，验证步骤要降级（只做静态检查和 Node 能跑的部分），或者依赖平台的其他执行环境（待确认） |

laoshi 现有的设计正好有两块可以直接用：

- **续跑**：引擎每一步的结果都存在 `state.json` 里，重新运行会跳过已完成的步骤（`laoshi resume`）。所以"每次调用只做一步"不需要重写流程。
- **平台用词和 skill 渲染**：skill 和提示词里与平台有关的说法都是 `{{platform.<词>}}`，按平台渲染（M2e），加一个平台只需要一份适配器。

## 2. 形态

```text
使用者 ──对话──► 摸高对话 agent（加载 laoshi 专家的 skill）
                     │ 每一轮：执行一条命令
                     ▼
     node /data/workspace/.laoshi/npm/…/req.mjs step <需求>      ← 一次执行做完一步
                     │ 读 state.json → 做下一步 → 校验结果、质量门 → 写回 → 输出"下一步"
                     ▼
            步骤 agent：B1 由引擎用 aimax run 起；B2 由对话 agent 自己（或它的子 agent）做
```

两种做法共用"每次调用只推进一步"这个核心，区别在于这一步谁来做：

| | B1：引擎在一次执行内做完一步 | B2：对话 agent 做这一步，引擎只发题和判卷 |
| --- | --- | --- |
| 命令 | `laoshi step <需求>`：起步骤 agent（`aimax run`），等它结束，校验、质量门，写状态 | `laoshi run next` 给出这一步的提示词和结果文件；对话 agent 做完后 `laoshi run record` 校验 |
| 需要平台提供 | `aimax run` 能在指定目录起一个 agent 并等到结束（或可轮询） | 只要对话 agent 能执行命令；有子 agent 工具更好 |
| 流程保证 | 强：和 Paseo、dsh 上一样，步骤、轮次、质量门都由引擎执行 | 较强：顺序和结果由命令校验，但对话 agent 可以不按流程走（[in-chat-orchestration](in-chat-orchestration.md) §4） |
| 独立评审 | 评审步骤是一个新的 agent，不带实现时的上下文 | 依赖子 agent；没有子 agent 时评审和实现是同一个上下文，独立性弱 |
| 适配器 | `adapters/mogao`：运行时用 `aimax run` 实现 `startAgent` / `wait`（同一次执行内） | 不需要运行时，只要用词和安装 |

**倾向 B1**，前提是第二轮确认 `aimax run` 可用；不可用时做 B2。两者都先需要引擎支持"只推进一步就退出"（见第 4 节第 2 项），所以这部分先做不会白做。

形态丙（纯 skill，不带引擎）始终可用：访谈、需求说明、验收标准、如实报告这些方法 skill 不依赖引擎，可以作为专家的最小版本先提交。

## 3. 安装

摸高上没有"安装器"这一步。专家的入口 skill 在第一次使用时：

1. 检查 `/data/workspace/.laoshi/npm` 下有没有约定版本的 `@yiyi_zhang/laoshi`，没有就 `npm install --prefix /data/workspace/.laoshi/npm @yiyi_zhang/laoshi@<版本>`（内网镜像，约十几秒）。
2. 写安装级配置：`platform.adapter = mogao`，各角色的模型默认用对话的模型（`AIMAX_MODEL`）。
3. 之后每条命令都写成 `LAOSHI_HOME=/data/workspace/.laoshi node /data/workspace/.laoshi/npm/node_modules/@yiyi_zhang/laoshi/bin/req.mjs …`（skill 渲染时把这一串换成占位符，使用者看不到）。

专家的 skill 由平台加载，不需要 laoshi 往平台目录里复制。专家提交时带上渲染好的 skill（平台用词 = 摸高）。

## 5. 参赛的亮点

- **不是写代码的助手，而是"把需求做到可验收"的专家**：给测试、产品、项目经理用，每个要拍板的地方都停下来等人。
- **流程由程序保证**：顺序、评审轮次、质量门、危险命令拦截、密钥扫描由引擎执行，不靠模型自觉。
- **能和平台已有的 skill 组合**：摸高上已有 SDD、PRD、测试用例等场景 skill，laoshi 的专家可以把它们作为某一步的方法（例如验收用例），体现"多 skill 组合"。
- **跨平台**：同一套流程已经在 Paseo、DeepSeek Harness 上运行，摸高是第三个平台。
- **结果可度量**：评估用例带隐藏验收，`laoshi stats` 统计交付周期、返工和等待。

## 6. 风险

- `aimax run` 不能在指定目录起 agent，或不能在一次执行内等到结束：只能做 B2，独立评审变弱。
- 单次执行有总时限，而一步（尤其是实现）超过时限：需要把一步拆成"起任务"和"查结果"两次执行，或缩小切片。
- Java 项目在沙箱里无法构建测试：验证步骤降级，要在报告里如实写明。
- 评审在谁的沙箱里试用、是否允许第一次使用时安装依赖：决定专家能否依赖 npm 包，否则要把程序随专家一起提交（S4）。
