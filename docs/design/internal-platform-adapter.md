# 内部 agent 平台适配：能力映射与缺口

- 状态：草案。**依据只有三条已知信息**，其余全部是待确认项，不能当作事实。
- 前置阅读：[agent-runtime.md](../../contracts/agent-runtime.md)、[init-bootstrap.md](init-bootstrap.md)

## 1. 已知

内部平台提供命令行（CLI），已知具备：

1. 启动 agent 任务；
2. 恢复"暂停中的 HITL（人在回路）会话"，传入用户输入后继续；
3. 取消"正在等待的 HITL 请求"。

## 2. 与 AgentRuntime 的对应关系

| 已知能力 | 最可能对应 | 需要确认的歧义 |
| --- | --- | --- |
| 启动 agent 任务 | `startAgent` | 能否指定工作目录、标题/标签、模型、权限模式；有没有"父会话"可以挂靠（`parentAgentId`） |
| 恢复暂停的 HITL 会话并传入输入 | 二选一：`StepAgent.followUp(text)`（在同一会话里开新回合），或"回答一个待处理的请求"（对应 `wait` 返回 `permission` 之后的批准/回答） | HITL 暂停是**一次回合结束后等你说下一句**，还是**agent 中途请求批准/提问**？两者在引擎里的处理完全不同 |
| 取消等待中的 HITL 请求 | "拒绝一个待处理请求"；**不等同于** `interruptAgent`（后者打断正在运行的回合并给出新指令） | 它能否取消一个**正在运行**的任务？如果不能，"停止步骤"只能退化为结束子进程 |

## 3. 必需能力里还不知道的部分

引擎要求必需能力全部可用。以下在已知信息里**没有出现**，是决定能否做适配器的关键：

| 必需能力 | 缺的是什么 | 如果平台没有 |
| --- | --- | --- |
| `StepAgent.wait` | 怎么知道任务"完成 / 暂停等人 / 出错 / 还在跑"：有没有状态查询命令？退出码？事件流？ | 适配器用**轮询**实现（定时调用状态命令直到不再是"运行中"）；没有任何状态来源则无法适配 |
| `attachAgent(id)` | 另一个进程能否凭任务 ID 查询状态、继续等待 | 续跑和"接着等上一次的 agent"会失效；退化为重新开始该步骤 |
| `notifyAgent` | 能否向一个**正在运行**的会话投递消息而不打断它 | 退化为写通知文件 + 外部通知器（`notifiers` 模块），进展不再进会话；使用者靠 `laoshi status` 查看 |
| `verifyOrigin` | 有没有"发起会话"的概念，环境里能否识别 | `identifyOrigin` 返回 `null`，只写日志；见 [adapter-guide §3](adapter-guide.md) |
| `interruptAgent` | 能否取消**运行中**的任务 | 若任务是本机子进程，可结束进程；否则该能力缺失，"停止"只能等当前步骤结束 |

可选能力（定时、工作区、服务、用量、活动……）全部未知，按 [agent-runtime.md](../../contracts/agent-runtime.md) 的降级行为处理即可，不阻塞第一个可用版本。

## 4. HITL 与引擎的关系（需要先对齐的设计问题）

req-kit 今天处理"等人"的方式：步骤 agent 请求权限 → `wait` 返回 `permission` 并附 `pendingPermissions` → 引擎把"请去批准"发到发起会话 → 由人在 Paseo 界面里批准 → 引擎轮询到它恢复。**引擎本身不替人批准。**

内部平台有"传入用户输入继续"和"取消请求"两个 CLI 动作，因此多了一种可能：由 laoshi 把人的回答**转交**给平台（例如 `laoshi reply`）。两种方式的取舍：

| | A：人在平台界面里处理，laoshi 只轮询 | B：laoshi 转交（用 CLI 恢复/取消） |
| --- | --- | --- |
| 需要的能力 | 只需"列出待处理请求" | 需要恢复、取消两个命令（已知具备） |
| 体验 | 和现在的 Paseo 一致 | 可以在同一个对话里完成，不用切到平台界面 |
| 风险 | 依赖平台有可用的处理界面 | 转交的是人的原话，要防止把 agent 输出或外部内容当作"用户输入"转交（只转交使用者在对话里明确说的话） |

倾向 B 作为主路径、A 作为兜底；**等确认 HITL 的真实语义（§2 第二行）后再定**。

## 5. 对描述解释器的要求

内部平台是"CLI + 轮询"形态，会对声明式描述提出这些要求（在 [init-bootstrap §3](init-bootstrap.md) 的示意之外补充）：

- **轮询式 `wait`**：声明状态命令、轮询间隔、"仍在运行"的判断条件，解释器循环直到条件不成立或超时。
- **多种终态映射**：命令输出里的状态值要映射到引擎的 `idle / error / permission / timeout`，并能提取 HITL 请求的 `id` 和 `title`。
- **长文本通过文件传参**：提示词很长，描述里用 `--prompt-file`、`--text-file` 这类占位符，不把文本拼进命令行。
- **凭据只走环境变量**：沿用 `daemonPasswordEnv` 的做法，不进描述、不进锁定文件。

## 6. 需要向平台方确认的问题（按重要性排序）

1. **状态**：怎么得知一个任务当前处于运行 / 完成 / 暂停等人 / 失败？有命令还是事件流？输出格式是 JSON 吗？
2. **HITL 的语义**：暂停发生在回合之间（等你说下一句），还是 agent 中途请求批准/提问？"取消请求"之后任务是继续、失败还是结束？
3. **会话与通知**：有没有"会话"可以让步骤任务挂靠？能否向运行中的会话发消息而不打断？
4. **控制**：能否指定工作目录、模型、权限模式？能否取消运行中的任务？能否同时运行多个任务？
5. **用量与凭据**：是否报告 token 用量（`budget` 功能依赖它，req-kit 对此有"没有用量就无法限额"的提示）？在无人值守的机器上怎么认证？

这五项里 1 和 2 决定"能不能做"，3 和 4 决定"体验是什么样"，5 决定"限额和成本统计能不能用"。
