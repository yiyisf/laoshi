# 安装与升级

本文面向负责安装的人：通常是开发同事，有经验的测试或产品同事也可以按步骤完成。每台机器只装一次（装在运行 agent 平台的那台机器上），之后这台机器上所有项目的对话都能使用 `/laoshi`。

laoshi 目前支持三个 agent 平台，另外可以不用平台、直接用编码 agent 命令行：

| 平台 | 说明 |
| --- | --- |
| [Paseo](https://paseo.sh) 0.11–0.17<br>`--platform paseo` | 步骤 agent、工作区、服务、定时消息都由 Paseo daemon 提供（优先 Web 端） |
| DeepSeek Harness（dsh）<br>`--platform dsh` | 步骤 agent 和定时消息由 laoshi 的 dsh 插件提供；工作区和服务用 laoshi 的内置实现（`git worktree`、`.laoshi/services.json`） |
| 命令行 agent<br>`--platform cli` | 不需要平台：步骤 agent 是 `claude -p` / `codex exec` 的一次运行；工作区和服务用 laoshi 的内置实现；没有通知发回对话，进展用 `laoshi status` 查看。见 [adapters/cli](../../adapters/cli/README.md) |
| 摸高<br>`--platform mogao` | 以专家的形式提交到平台，第一次使用时自动装到工作区，不按本文安装；见[在摸高上使用](在摸高上使用.md) |

## 1. 安装布局

程序和本机配置分开存放。升级只替换程序，配置不动。

```text
<npm 全局目录>/laoshi/     程序（全局目录不可写时在 ~/.laoshi/npm 下）
~/.laoshi/                 安装根（LAOSHI_HOME 可以换位置）
├── config.json            安装级配置：平台、各角色的模型
├── install.json           安装记录（--check、--uninstall 用）
├── bin/laoshi(.cmd)       laoshi 命令（不在 PATH 时用）
├── prompts.local/         本机提示词覆盖（可选）
└── notifiers/             外部通知模块（可选，见第 10 节）
<skill 目录>/laoshi*/      按平台渲染的 skill，带 .laoshi-install.json
```

skill 装到哪里由平台决定：

| 平台 | skill 目录 |
| --- | --- |
| Paseo | `~/.agents/skills`（Codex、Pi、OpenCode 等读取），`~/.claude` 存在时还有 `~/.claude/skills` |
| 命令行 agent | 与 Paseo 相同 |
| dsh | `$DSH_HOME/skills`（默认 `~/.dsh/skills`）；dsh 插件装在 `$DSH_HOME/profiles/<profile>/node_modules/laoshi-dsh-plugin` 并挂载到 `cordis.patch.yml` |

`--target <目录>` 可以另外指定 skill 目录（可以写多次）。Windows 上 `~` 即 `%USERPROFILE%`。安装器不使用符号链接，不需要管理员权限；在 Windows 上它只启动 `node` 和 `cmd.exe`，不会启动 PowerShell。

## 2. 前置条件

| 项目 | 要求 | 如何确认 |
| --- | --- | --- |
| Node.js | 22.19 或更新 | `node -v` |
| npm | Node.js 自带；公司网络用镜像（见第 3 节） | `npm -v` |
| git | 近期版本 | `git --version` |
| 平台 | Paseo 0.11–0.17 的 daemon 在运行；或已装好 dsh（`dsh` 命令可用，或知道它的 `bin.js` 位置） | Paseo：能在网页端（`http://localhost:6767/`，推荐）或桌面端对话；dsh：能在网页端对话 |
| 模型 | Paseo：Claude Code、Codex、OpenCode、Pi 至少一种已在 Paseo 中登录；dsh：对话用的模型能正常回答 | 用它开一个对话 |

## 3. 首次安装

**一步安装（推荐）。** 只需 Node.js、git 和能访问的 npm 源，**一条命令**即可装好 `laoshi` 程序本身、配置、skill 以及对应平台的需求插件：

```bash
npx -y @yiyi_zhang/laoshi@latest install --platform dsh      # 或 --platform paseo
# 如需体验测试版，把 @latest 换成 @beta
```

它依次：检查 Node.js、npm 和 git；确定 npm 源；`npm install -g` 这个版本（全局目录不可写时装到 `~/.laoshi/npm`，不需要 sudo）；然后自动运行装好的那份程序的 `laoshi install`，一次性完成安装级配置、skill 渲染，以及对应平台的插件部署与挂载（dsh 会安装 `laoshi-dsh-plugin` 并挂载左栏「需求看板」；Paseo 会默认部署并加载 `laoshi` 插件，如未启动 daemon 则提示启动后补注册）。npx 的临时目录会被清理，所以安装记录和 skill 都指向 npm 装好的那份。再次运行就是升级。

指定版本：`npx -y @yiyi_zhang/laoshi@0.3.1 install --platform dsh`。

> **同机多平台并存**：同一台机器已经装过一个平台（例如 `paseo`）时，再执行 `npx -y @yiyi_zhang/laoshi@latest install --platform dsh`（或 `laoshi install --platform dsh`），会在同份 `~/.laoshi/config.json` 中保留原有默认平台，同时添加并存平台 `platform.<平台>` 配置和该平台独立的 skill/插件，互不覆盖。

**公司内网（只有 npm 镜像）。** 加上镜像地址：

```bash
npx -y --registry=https://npm.example.internal/ @yiyi_zhang/laoshi@latest install --platform dsh
```

- 镜像地址会**保存为本机的 npm 源**（屏幕上会写出原来的值），以后 `laoshi upgrade` 也从镜像取。只想这一次用镜像时加 `--no-save-registry`。本机原本就配好了镜像时不用写 `--registry`。
- 镜像上还没有这个版本（同步有延迟）时会直接说明，稍后再运行，或请管理镜像的同事同步 `laoshi`。
- 文档：装好后运行 `laoshi docs`，在本机打开和这个版本一致的文档站点，不需要外网。

**完全离线（连 npm 镜像也没有）。** 用带依赖的离线安装包，步骤见[内网安装与验证](../intranet/install-verify.md)。

**已经有程序目录时**（git 克隆、解压的安装包）：在程序目录中 `npm ci --omit=dev`，再运行 `node bin/req.mjs install --platform <平台>`。

### 安装选项

| 选项 | 含义 |
| --- | --- |
| `--platform <paseo\|dsh\|cli\|mogao>` | 装到哪个平台。第一次安装时要写；已有安装配置后再安装另一个平台会以并存方式加入；省略 `--platform` 时会更新已安装的全部平台 |
| `--home <目录>` | 安装根，默认 `LAOSHI_HOME` 或 `~/.laoshi` |
| `--target <目录>` | 另外把 skill 装到这个目录 |
| `--force` | 覆盖同名的、不是 laoshi 装的 skill（默认跳过并列出） |
| `--check` | 只检查，不改动（也可以用 `laoshi check`） |
| `--dry-run` | 演练：显示要做的事，不写文件 |
| `--uninstall` | 卸载指定平台（默认或 `--platform <平台>`）的 skill 和插件；有多平台并存时保留其余平台与安装根 |
| `--registry <地址>`、`--no-save-registry` | 只用于一步安装和 `laoshi upgrade`：这次用的 npm 源，是否保存 |
| `--allow-running` | 仅用于 `laoshi upgrade` / 一步升级：若检测到有正在运行的流水线，仍强制原地升级 |
| Paseo：`--no-plugin` | 安装时跳过自动部署和加载 Paseo 需求插件（旧写法 `--with-plugin` 仍兼容保留） |
| dsh：`--dsh-home <目录>` | dsh 的数据目录，默认 `DSH_HOME` 或 `~/.dsh` |
| dsh：`--profile <名称>` | 插件装进哪个 profile，默认 `web` |
| dsh：`--dsh-bin <路径>` | dsh 的 `bin.js`，`dsh` 不在 PATH 中时写；`dsh plugin add` 失败时安装器直接复制插件 |
| dsh：`--approvals ask\|allow` | 步骤 agent 的审批请求：`ask` 交给人（默认），`allow` 直接批准一次 |
| dsh：`--no-board` | 关闭安装后默认随 dsh 启动并挂载到左侧导航栏「需求看板」的托管需求看板（默认开启 `board: true`） |
| dsh：`--board-port <端口>` | 固定 dsh 托管需求看板底层监听的本地端口（默认自动分配空闲端口；正常使用推荐直接在 dsh 左侧栏点击「需求看板」打开） |

同名 skill 的处理：带 `.laoshi-install.json` 标记的是 laoshi 装的，会被更新；paseo-req-kit 装的（带 `.req-kit-install.json`）和别人放的都不覆盖，安装器会列出它们，确认后再用 `--force`。

## 4. 配置模型

各角色（builder 实现、reviewer 评审等）用的模型写在 `~/.laoshi/config.json` 的 `agents` 中，项目的 `.laoshi.json` 可以覆盖。写法因平台而异。

### Paseo

运行 `laoshi configure`（逐项选择）或 `laoshi configure --auto`（按推荐选好：两个不同厂商的模型分别做 builder 和 reviewer，都用免确认模式）。

**推荐引用 Paseo 的 agent profile。** 在 Paseo 的 设置 → 本机 → Agents → Agent profiles 中建好"实现""评审"等 profile，配置中只写名称，之后换模型只需在 Paseo 中改 profile：

```json
"agents": {
  "builder":  { "platformProfile": "实现" },
  "reviewer": { "platformProfile": "评审" }
}
```

也可以直接写各项设置：

| 字段 | 含义 |
| --- | --- |
| `provider` | `<Paseo 中的 provider ID>/<模型 ID>`，只在第一个 `/` 处拆分 |
| `modeId` | agent 的模式。必须选不会停下来等待批准的模式；没有模式的 agent 不写 |
| `featureValues` | agent 的功能开关，目前只有 OpenCode 需要 |
| `thinkingOptionId` | 可选，思考强度 |

| agent | `provider` 写法 | 无人值守的设置 |
| --- | --- | --- |
| Claude Code | `claude/<模型 ID>` | `"modeId": "bypassPermissions"` |
| Codex | `codex/<模型 ID>` | `"modeId": "full-access"` |
| OpenCode | `opencode/<上游>/<模型 ID>` | `"modeId": "build"` 加 `"featureValues": { "auto_accept": true }` |
| Pi | `pi/<上游>/<模型 ID>` | 不写 `modeId` |

聊天 agent（使用者对话的那一个）的用法：

| agent | 如何触发 |
| --- | --- |
| Claude Code、OpenCode | `/laoshi 我想……` |
| Pi | `/skill:laoshi 我想……` |
| Codex | 直接说"用 laoshi 帮我……" |

聊天 agent 需要能执行命令和访问本机网络（流水线要连接 daemon）。

### dsh

`provider` 写成 `<dsh 的提供方>/<模型>`，这个角色的步骤就用它；`thinkingOptionId` 作为推理强度。`dsh/chat-model` 表示用对话的模型（安装器的默认值）：

```json
"agents": {
  "builder":  { "provider": "dsh/chat-model" },
  "reviewer": { "provider": "deepseek/deepseek-reasoner", "thinkingOptionId": "high" }
}
```

`laoshi doctor` 列出 dsh 中可用的模型并逐个角色检查。在 dsh 的对话里输入 `/laoshi 我想……` 开始；发起的对话由 dsh 提供的 `DSH_SESSION_ID` 识别。更多见[在 DeepSeek Harness 上使用](../../adapters/dsh/README.md)。

## 5. 体检和冒烟测试

```bash
laoshi doctor --no-project    # 安装、配置、平台、模型
laoshi doctor                 # 在项目目录中：再检查这个项目
```

全部是 ✓ 或只有 ⚠ 即可继续，✗ 的项按提示处理。然后在一个测试项目中完整跑一遍：新开对话，输入 `/laoshi 在 README 末尾加一行版权声明`，应走快速档，收到进展和完成通知，功能目录中各产物齐全，工作分支上有本地提交。

Paseo 另有冒烟测试（在程序目录中运行）：`npm run smoke -- check` 启动两个角色各一个小 agent，确认能写文件、能执行命令、不停下等权限。

## 6. 升级和回退

**一条命令同时升级 `laoshi` 与全部已装平台的 skill / 插件**：

```bash
laoshi upgrade                       # 升级到最新正式版（同时刷新全部已并存平台的 skill 和插件）
laoshi upgrade beta                  # 升级到最新 beta 测试版
laoshi upgrade 0.3.1                 # 指定版本（也用于回退到旧版本）
laoshi upgrade --registry <镜像地址>  # 换 npm 源
```

它依次执行：

1. 扫描安装根（`~/.laoshi/index/`）下各代码库是否有**正在运行或等待中的流水线**（ADR 0007）：如果有运行中的流水线，默认列出项目、需求目录、当前步骤与进程 PID 并中止，以免原地替换文件影响运行（等待确认/回复的需求不受影响；确需强行继续可加 `--allow-running`）。
2. 从 npm 装好新版本程序，随后自动运行新版本的 `laoshi install`（不带 `--platform` 时会自动遍历刷新安装记录中的所有并存平台，例如同时刷新 Paseo 与 dsh 的 skill 及插件）。配置、项目文件和功能目录不变；dsh 插件会先清理旧版并完整覆盖最新文件，无需手工先卸载旧插件。

平台（Paseo、dsh）或 agent 升级之后，运行 `laoshi doctor`（切换检查并存平台可设 `LAOSHI_PLATFORM=<平台> laoshi doctor`）确认版本在支持范围内、配置中的模型仍然存在。

## 7. 和 paseo-req-kit 共存

laoshi 是从 paseo-req-kit 抽出的平台无关版本，两者可以装在同一台机器上：

- 安装根不同（`~/.laoshi` 和 `~/.req-kit`），命令不同（`laoshi` 和 `req`；laoshi 也提供 `req` 别名，npm 全局安装时后装的那个生效）。
- 只有 `~/.req-kit` 时，laoshi 会读取它；`.requirement-pipeline.json` 也继续被读取，新项目用 `.laoshi.json`。
- 同名 skill 不互相覆盖（见第 3 节）。

**从 paseo-req-kit 迁移**：`laoshi migrate` 把本机 `~/.req-kit` 的配置、使用记录、需求索引、本机提示词和通知模块搬到 `~/.laoshi`，并把进行中需求的旧格式状态文件改为新格式（原文件保留为 `state.json.bak-v1`）。

```sh
laoshi migrate            # 预览：列出会做什么，不改任何东西
laoshi migrate --apply    # 执行；有流水线正在运行时会拒绝
laoshi migrate --rollback # 回滚：恢复状态文件、删除迁移写入的文件，接着用 paseo-req-kit
laoshi install --platform paseo   # 迁移后安装 /laoshi* skill
```

- 旧目录 `~/.req-kit` 不改、不删，回滚后 paseo-req-kit 照常可用。
- 配置里的 daemon 地址移到 `platform.paseo`，旧的 profile、服务字段改为新名字。
- 项目里的 `.requirement-pipeline.json` 不改名（laoshi 照常读取），要改名请在仓库里改名后提交。
- 设置过 `REQ_KIT_HOME` 的，迁移后改为设置 `LAOSHI_HOME`。

## 8. 卸载

```bash
laoshi install --uninstall                 # 卸载默认平台
laoshi install --platform dsh --uninstall  # 多平台并存时，仅卸载指定平台
```

删除该平台下由 laoshi 装的 skill，dsh 上还会移除 `laoshi-dsh-plugin` 和 `cordis.patch.yml` 中的挂载，Paseo 上会移除 Paseo 插件。当机器上还保留着其他并存平台时，共用配置文件与 `bin/laoshi` 命令会自动保留；所有平台都卸载后，安装根（`~/.laoshi`）仍保留（含配置与使用记录），确认不再使用后可运行 `npm uninstall -g @yiyi_zhang/laoshi` 并手工删除 `~/.laoshi`。各项目中的配置文件和功能目录保留，它们本身就是文档。

## 9. 安全提示

- 步骤 agent 以免确认模式运行（dsh 上 `--approvals allow` 时同样），可以在本机执行命令。仓库和本机环境变量中不要放生产凭据；最好用专门的开发机或虚拟机。
- 口令和密钥只放在环境变量中，不要写进配置文件。
- 流水线只做本地提交，合并和上线始终由人决定。

## 10. 接入企业内部 IM（可选）

流水线默认只把消息发回发起的对话。希望"需要你决定""开发中断""已完成"等时刻在企业 IM 中也收到时，需要自己实现一个通知模块（laoshi 不内置任何 IM）：

1. 把程序目录中的 `notifiers/im-template.mjs` 复制到 `~/.laoshi/notifiers/im.mjs`，按其中的 TODO 实现发送（通常是向 IM 机器人的 webhook 发一个 HTTP 请求）。口令放在环境变量中。
2. 在 `~/.laoshi/config.json`（或团队配置）中加上：

   ```json
   "notifiers": [
     { "module": "~/.laoshi/notifiers/im.mjs", "events": ["blocked", "failed", "completed"], "options": { "webhook": "https://…" } }
   ]
   ```

3. 运行 `laoshi notify-test`（可加 `--type blocked` 等）发一条测试消息。

事件的类型和字段见 [contracts/notifier-event.md](../../contracts/notifier-event.md)。通知失败只记日志，不影响流水线。项目配置（`.laoshi.json`）中的 `notifiers` 会被忽略。

## 11. 平台需求插件与共享 Web 需求看板

在 Paseo Web 端与 DeepSeek Harness（dsh）Web 端界面（以及命令行 `laoshi board`）里查看需求总览、进度、文档、阶段执行记录、变更历史与负责人，确认方案、发起改需求、转交、停止、继续、一键试用、验收及选择模型的插件，随 `laoshi install` / `laoshi upgrade` 一步安装并同步更新：

```sh
laoshi install --platform dsh                     # 一步安装/刷新 dsh skill、插件及左栏「需求看板」(`/laoshi/`)
laoshi install --platform paseo                   # 一步安装/刷新 Paseo skill 及需求插件（跳过插件加 --no-plugin）
laoshi plugin install [--yes]                     # Paseo 单独补装或重载（如安装时 daemon 未运行）
laoshi plugin status                              # Paseo 插件是否在运行
laoshi plugin remove                              # 从 Paseo 移除
laoshi board                                      # 任意平台随时单独打开共享 Web 需求看板
```

### DeepSeek Harness（dsh）内嵌需求看板与全宽详情页

- 重启 `dsh`（`dsh --profile web`）后，左侧导航栏会出现 **「需求看板」** 入口（`/laoshi/`），直接在 dsh 主界面内嵌打开，并自动随 dsh 切换深浅主题、复用 dsh 登录校验；顶部导航支持切换 **需求 / 使用统计 / 配置**。
- 看板列表与详情采用与 Paseo 一致化的**全宽页面**布局（`← 返回需求列表`、关键决策高亮操作区、代码审查 / 审查原型外链、2 列元数据卡片、Markdown 渲染与 TSV 表格文档弹窗、以及完整的 **「执行记录」** 与 **「验收工作台」** / **「变更与接手」** 子页）。
- 点击某一步的 **「查看执行记录 ↗」** 或详情顶部的 **「打开需求对话 ↗」** 可直接在 dsh 中跳回对应子 agent 或原需求对话；在需求主对话或步骤子对话窗口中，顶部栏也会显示 **「需求：<标题>」** 快捷按钮，一键切换到内嵌「需求看板」的对应需求详情。
- 从旧版升级 `laoshi install --platform dsh` 或 `laoshi upgrade` 时，无需先卸载旧版 `laoshi-dsh-plugin`，安装器会自动完整覆盖插件文件并在 `cordis.patch.yml` 中更新 `kitRoot`、补齐 `board`，同时保留原有的 `approvals` 等设置。

### Paseo 需求插件（`adapters/paseo/plugin`，适配 Paseo `0.11–0.17`）

- 安装 `paseo` 平台时默认将插件复制到 `<安装根>/paseo-plugin` 并自动加载到 Paseo（若当时未运行 daemon 或无 `paseo` 命令，文件仍会提前就绪，待启动 Paseo 后运行 `laoshi plugin install` 或在 Paseo 「设置 → Plugins」手动填入该路径）；此后每次 `laoshi install`、`laoshi upgrade` 都会顺带刷新并重载插件，确保版本一致。
- 插件只在本机运行 `laoshi api`（[cli-json](../../contracts/cli-json.md)），不连接外部服务；插件设置里可以打开"只读"，只看不改。
- 插件默认读取 `LAOSHI_HOME` 或 `~/.laoshi`；如果在安装时使用了非默认的 `--home` 目录（尤其在 Paseo 0.17 下，服务端插件经打包执行没有 `import.meta.url`），需确保守护进程环境变量中有对应的 `LAOSHI_HOME`，或在 Paseo「设置 → 插件 → laoshi → laoshi 的安装根」中填写实际安装根路径。
- 装过 paseo-req-kit 的插件（id `req-kit`）：两个可以同时存在，迁移到 laoshi 后用 `req plugin remove` 移除旧的。
- 没有 `paseo` 命令（桌面版 Paseo 管理的 daemon）时，按提示在 Paseo 的 设置 → Plugins 中手动填插件目录。
