# 维护者指南

面向维护 laoshi 本身的人：改提示词和 skill、发布新版本、处理复盘提交的问题。

## 1. 改动之前

- 先看 [SCOPE.md](../../SCOPE.md)：新提议须服务于"帮助非专职开发的同事把一个需求从对齐做到可验收"，至少有两个真实场景，并且无法通过项目配置或项目说明解决。
- 改动已有的设计决定（[docs/adr/](../adr/)）时，新增一条 ADR 说明理由，并在旧的一条中注明被哪条取代。
- 界面的颜色、字体、组件按 `design/`（设计规范，见其中的 README）来；改了 `design/tokens.json`、`design/reference/components.css` 或 `design/examples/icons.js`，运行 `node scripts/tokens-build.mjs` 更新审查网页里的副本。
- 改动文件格式（spec、状态文件、结果文件、决策记录等）时，同时更新 [contracts/](../../contracts/)、代码和测试；状态文件的格式变化要加迁移（见 `contracts/state.md`）。

## 2. 改 skill 和提示词的规则

- **入口不调用入口**。`/laoshi`、`/laoshi-setup`、`/laoshi-doctor`、`/laoshi-retro` 之间只能"告诉用户去运行"，不能互相加载。
- **路径用占位符**：skill 中引用安装目录内的文件写 `{{REQ_KIT_ROOT}}/...`，启动命令写 `{{PIPELINE_LAUNCHER}}`，版本号写 `{{REQ_KIT_VERSION}}`。安装器会替换它们；`npm test` 会检查引用的文件都存在。
- **不写平台的名字**：引擎、提示词和 skill 中和平台有关的说法写成 `{{platform.<词>}}`（见 [platform-vocabulary](../design/platform-vocabulary.md)），整段不同的写成 `{{fragment.<名称>}}`，各平台的片段放在适配器里（如 `adapters/paseo/skill/setup.md`）。`npm test` 会检查这些目录中没有平台的名字；确实需要时在那一行写 `platform-name:` 说明理由。
- **frontmatter** 只用 `name`、`description`，agent 专属的放在 `metadata` 下；`description` 中不要出现半角的 `: `。
- **手册**（`skills/laoshi/playbooks/*.md`）开头必须有"## 步骤"编号列表，`/laoshi` 会把它原样放进待办列表；新增手册要加进 `/laoshi` 的路由表。
- **原则**：增加一条原则需要至少两次真实失误作为依据，并且无法用 CI 或配置解决；总数不超过 10 条。原则的一句话版本写进 `principles/INDEX.md`，它同时被聊天和每个步骤的提示词使用。
- **措辞**：读者是有技术背景、但不读代码的使用者（测试、产品、项目经理）。讲需求和结果，不讲代码实现。

## 3. 验证改动

| 改了什么 | 至少要做 |
| --- | --- |
| 引擎代码 | `npm test`、`npm run typecheck` |
| 步骤提示词 | 上面两项 + `npm run eval`（至少跑受影响的用例），与上一次的结果对比 |
| 入口、手册、方法 skill、原则 | `npm test` + 对话评估中受影响的剧本（`evals/conversation/`） |
| 安装器 | `npm test`（在临时 HOME 中测试），并在 Windows 上实际装一次（只用 cmd 或 Git Bash） |
| 评估用例 | `npm run eval:self-check`（参考实现必须通过隐藏验收） |
| 平台适配器 | `npm test`；dsh 另跑端到端检查 `node adapters/dsh/e2e/run-e2e.mjs --worktree`（见 [adapters/dsh/README.md](../../adapters/dsh/README.md)）；Paseo 另跑 `npm run smoke -- check` |
| 文档站点 | `cd site && npm ci && npm run build`（会检查站内链接） |

提示词改动以评估结果为准：如实率（不夸大）不能下降；隐藏验收通过率、用时、轮次与上一次对比，变差时说明原因。

## 4. 发布

版本号遵循语义化版本，从 `0.1.0` 开始，标签**不带 `v` 前缀**（例如 `0.1.0`、`0.2.0-beta.1`）。laoshi 和 paseo-req-kit 一样通过 npm 分发：使用者用 `npx -y @yiyi_zhang/laoshi@latest install` 安装，用 `laoshi upgrade` 升级，内网通过公司的 npm 镜像取得。

开发中的版本号带 `-dev`（如 `0.2.0-dev`），不会被发布。发布一个版本：

1. 在 `CHANGELOG.md` 中把这一版写成 `## <版本> - <日期>` 一节：使用者会看到的变化在前，升级须知单独列出。发布流程用这一节作为 GitHub Release 的正文，没有这一节时停下。
2. 把 `package.json` 的 `version` 改成这个版本（去掉 `-dev`）；平台支持范围有变化时同时更新 `reqKit.paseo`。
3. 跑完第 3 节中受影响的验证，并在 Windows 上实际装一次（`node scripts/check-package.mjs` 检查装出来的包）。
4. 合并到 `main`。`.github/workflows/release.yml` 发现这个版本号还没有标签，就在这个提交上跑测试（Linux 和 Windows）、类型检查、评估自检，把文档站点构建进包里（`site-dist/`，`laoshi docs` 离线可用），`npm pack` 后用 `scripts/check-package.mjs` 按使用者的方式安装检查，再做 Windows 离线安装包。全部通过后才打上同名标签（不带 `v`），发布到 npm（预发布版用 `beta` 标签，正式版用 `latest`），并建 GitHub Release，附上 `.tgz` 和离线安装包。测试没通过时不会留下标签，把修复合到 `main` 就会用同一个版本号重新发布。
5. 发布后把 `version` 改回下一个开发版本（如 `0.2.0-dev`）。

也可以自己推送标签（`git push origin 0.1.0`）触发；重新发布已有的标签：GitHub → Actions → release → Run workflow，填版本号。npm 上发布错的版本用 `npm deprecate` 标注（npm 不允许重新发布同一版本号）。

**npm 发布的一次性设置**：

1. 包名是带作用域的 `@yiyi_zhang/laoshi`（`laoshi` 在 npm 上不能使用），作用域 `yiyi_zhang` 就是发布者的 npm 用户名。在 npmjs.com 上用这个账号建一个 Granular Access Token：权限 Read and write，Packages 选 All packages，并勾选 **Bypass two-factor authentication**（CI 里没法输入一次性验证码）。在 GitHub 仓库的 Settings → Secrets and variables → Actions 中新建 secret `NPM_TOKEN`，值为这个 token。不要把 token 写进任何文件或发给别人。
2. 第一次发布成功后，在 npmjs.com 的 `@yiyi_zhang/laoshi` 包设置 → Trusted Publisher 中添加 GitHub Actions：仓库 `yiyisf/laoshi`，工作流 `release.yml`。之后发布不再需要 token，可以删除 `NPM_TOKEN`。
3. 文档站点：Settings → Pages → Source 选 "Deploy from a branch"，分支 `gh-pages`，目录 `/`（`.github/workflows/site.yml` 在 main 更新时发布）。

**企业私有仓库**：只代理 npmjs 的不用做什么。需要单独发布到内网仓库时，从 GitHub Release 下载 `laoshi-<版本>.tgz`（或 `npm pack` 得到 `yiyi_zhang-laoshi-<版本>.tgz`），执行 `npm publish <这个文件> --registry <内网地址> --tag <同名标签>`。完全没有 npm 镜像的环境用 GitHub Release 上的离线安装包（`laoshi-<版本>-<提交>-win32-x64.zip`，也可以自己运行 `node scripts/pack-intranet.mjs`），见[内网安装与验证](../intranet/install-verify.md)。

**对外约定**：通知事件（`contracts/notifier-event.md`）由各团队自己的 IM 模块读取，同一 `schema` 内只增加字段；`laoshi` 的子命令和参数会被写进各团队的使用说明，改名时保留旧名一个主版本（`req` 是 `laoshi` 的别名）。`laoshi api` 的输出（`contracts/cli-json.md`）是插件和脚本读取的格式，同一 `schema` 内只增加字段。

## 5. 处理复盘提交的问题

`/laoshi-retro` 会把 laoshi 本身的问题写成报告草稿交给用户。收到后：

1. 能复现的，先加一个评估用例或对话剧本，确认它在当前版本失败。
2. 修改后跑同一个评估，确认修好，并且其他用例没有变差。
3. 在 CHANGELOG 中记录。

## 6. 目录速查

| 目录 | 内容 |
| --- | --- |
| `skills/` | 安装到各平台的 skill（安装时按平台渲染）：入口、手册、方法、原则 |
| `principles/INDEX.md` | 原则索引 |
| `engine/src/` | 引擎：启动器、主流程、配置、状态与迁移、体检、评估运行器 |
| `engine/prompts/` | 步骤提示词（含 `00-shared-context.md` 和评审小组成员的 `panel-member.md`） |
| `engine/test/` | 引擎测试，`fake-runtime.ts` 是模拟的平台 |
| `engine/src/builtin/` | 内置能力：`git worktree` 工作区、服务管理（平台不提供时使用） |
| `engine/skill-fragments/` | skill 中各平台共用的内置片段 |
| `adapters/<平台>/` | 平台适配器：`adapter.ts`（能力和用词）、运行时、`install.mjs`（安装器的平台部分）；dsh 另有插件 `plugin/` 和端到端检查 `e2e/` |
| `bin/` | `laoshi` 命令、安装器（`install.mjs`）、一步安装（`bootstrap.mjs`）、`laoshi docs` |
| `site/` | 文档站点（VitePress）；`site/scripts/sync-docs.mjs` 把 `docs/guide`、`contracts` 等复制进站点 |
| `test/` | 安装器、体检、skill 的测试 |
| `evals/` | 评估：样例仓库、用例、对话剧本 |
| `contracts/` | 文件格式约定 |
| `docs/adr/` | 设计决定 |
| `design/` | 界面设计规范：tokens、品牌手册、各界面规范、组件、效果图 |
