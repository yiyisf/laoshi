# 0006 确定性引擎 + 平台能力层：先手写，后生成

- 状态：提议（项目负责人已同意方向，待摸底实验结果确认）
- 日期：2026-10-25
- 关联：[ADR 0001](0001-new-repo-core-and-adapters.md)、[ADR 0002](0002-two-orchestration-modes.md)、[ADR 0003](0003-generate-once-then-lock.md)

## 背景

AI loop 摸高项目要在公司自建的 agent 平台上做第一个试用，同时项目目标是通用适配，不绑定单个平台。已确认：摸高平台与"有命令行、能启动任务、恢复和取消 HITL"的内部平台是同一个平台。

平台提供 JS 动态工作流，也允许在主会话里手动发起子 agent。

## 决定

1. **不使用平台自带的动态工作流**。它和 laoshi 的引擎编排重叠，会让流程规则出现两份。
2. **最终形态是确定性步骤编排（引擎），不是 AI 在会话里编排**。顺序、重试、超时、关卡由引擎决定；AI 只在步骤内工作。模式 B（会话内编排，见 ADR 0002）仍是有条件的备选，不进主路径。
3. **引擎统一提供；依赖平台的能力在目标平台上探测后补充实现**。实现形式不限（命令行调用、脚本、少量代码），验收标准是契约一致性测试和探针通过，而不是实现形式。
4. **步骤 agent 优先用平台命令行起任务**；主会话子 agent 只作为可选能力，不进主路径。
5. **先手写、后生成**：
   1. 第一个内部平台适配器由人依据摸底结果手写；
   2. 探针与一致性测试（`runConformance`）先于任何生成；
   3. 手里有至少两个手写适配器（Paseo、内部平台）作样本和真值后，再让 LLM 起草适配器，经人审阅后锁定（ADR 0003），并用已知平台反向验证它能复现手写版本。

## 理由

- 确定性骨架加步骤内 AI 是业界成熟做法（Anthropic 的 workflow 与 agent 区分；Archon 等）。
- 多 agent 适配在业界都是人手写适配器（ACP、agentapi），没有找到"LLM 自行生成并锁定平台适配器"的公开先例；论文里 OpenAPI 到 MCP 的自动生成也要靠规范修复和测试把关。
- 通用性的证据来自契约、一致性测试和两个以上适配器，不依赖自动生成。

## 前置事实（摸底实验 1~3 回答）

1. 引擎进程能在哪里运行：沙箱里是否有 Node、能否安装依赖、后台进程能存活多久、能否调用平台命令行。
2. 命令行能否起任务并查询状态，状态取值有哪些。
3. HITL 的真实语义（回合之间还是中途提问；取消请求后任务如何）。

三项里任何一项答案为"否"，需回到本 ADR 重新评估引擎的位置与 `wait` 的实现方式。

## 影响

- 计划中内部平台适配器（M4）优先级提高，与无头 CLI 运行时（M3）并行；初始化与生成（M5）排在两个手写适配器之后。
- 平台摸底清单从"了解平台"升级为"决定引擎放哪、`wait` 怎么实现、HITL 怎么映射"的依据。
- 不改变对外契约（ADR 0004）。
