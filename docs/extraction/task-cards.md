# 任务卡：每个角色做什么、怎么做、怎么算完成

- 配套：[workstreams.md](workstreams.md)（角色、依赖、阶段门槛）、[plan.md](plan.md)（里程碑）、[ADR 0006](../adr/0006-deterministic-engine-platform-capabilities.md)
- 说明：命令和文件名来自 req-kit 1.13 的真实内容（`package.json`、`evals/README.md`、`engine/test/`）。标"待 X 确认"的地方是现在还不知道的事实，不要猜。
- 通用要求：每张卡的"怎么复核"由**另一位成员**执行一遍；产出里不放令牌、密码和内部地址。

## A 平台摸底

**目标**：用实验回答"引擎放哪、`wait` 怎么实现、HITL 怎么映射"，让 D 可以开工。

**输入**：[platform-discovery.md](../design/platform-discovery.md)（实验 A、0、1、2a、2b、2c、3、4）。

**做法**
1. 在摸高平台的沙箱里新建空的临时目录，所有实验在里面做。每次命令的完整命令行、stdout、stderr、退出码原样存文件。
2. 先做**实验 A**：Node 和 npm 是否有；`npm install` 一个小包是否成功；平台命令行能否在沙箱里执行；后台进程 5 分钟、30 分钟后是否存活；工作区外目录下次对话是否还在；4 GB 够不够。
3. 再做实验 0、1、2a、2b、2c、3、4。
4. 补三项清单里没有的实验：
   - 命令行起的任务**能不能调用平台技能**（版本计划、需求、用例、wiki）；怎么调用、参数是什么。
   - 主会话手动发起子 agent：谁触发、能否并行、结果怎么取回、有无超时（只记录，不进主路径）。
   - 沙箱里 `repos/` 多仓库布局下，任务的工作目录能否指定到某个仓库。
5. 按 `report.md` 的表填"是 / 否 / 不确定 + 依据文件名"。

**产出**：实验文件夹（脱敏）和 `report.md`。

**怎么复核**：另一位成员任选一个实验（建议实验 2a）按文档重做，结果与记录一致。

**完成标准**：`report.md` 每行都有答案，"不确定"不超过 2 项，并写明为什么不确定。预计 1~2 小时，加补充实验约半天。

**不做**：不写适配器代码；不改平台配置。

## B 基线与环境

**目标**：拿到 req-kit 1.13 的可复现基线，作为所有"行为不变"的比较对象。

**做法**
1. 找一台能 `npm install` 的机器（内网源已设好，无需指定）。克隆 `paseo-req-kit` 到 tag `v1.13.0`（对应提交 `4bdb338`）。
2. 依次运行并记录通过数、失败数、耗时、Node 版本：
   ```bash
   npm install
   npm run typecheck
   npm test            # 模拟 Paseo，几分钟；已含"每个用例的参考实现必须通过隐藏验收"的检查
   npm run eval:self-check   # 用参考实现检查评估用例本身，秒级，不需要 Paseo
   ```
3. 每条命令各跑两次，标出不稳定（时过时不过）的测试。
4. `npm run eval`（真实 Paseo 和 agent，每个用例几十分钟到几小时）：只有环境里装了 Paseo 才跑；没有就写"未取得"，不要跳过不说。
5. 写一页"开发环境说明"：Node 版本、安装步骤、常见错误，让 C、E 能直接用。

**产出**：`evals/baselines/1.13.0.md`（含上面的表和"未取得"项）、环境说明。

**怎么复核**：另一位成员在另一台机器按说明装一遍，三条命令结果一致。

**完成标准**：`typecheck`、`npm test`、`eval:self-check` 在两次运行里结果一致并有记录。预计半天。

**不做**：不改 req-kit 代码。

## C 核心搬运与拆耦合（里程碑 M1、M2）

**目标**：把核心搬进 laoshi，行为不变；然后把平台名拆出核心。

**输入**：[asset-inventory.md](asset-inventory.md)、[architecture §5](../design/architecture.md)、B 的基线。

**做法（M1，先做）**
1. 按资产清单搬运：方法类 skill 与原则、步骤提示词、`engine/src` 核心文件、`engine/test`、`evals/`。**文件路径和名字保持不变**。
2. 把 `paseo-runtime`、`paseo-profiles`、`paseo-json`、`daemon-check`、`daemon-version` 移到 `adapters/paseo/`；`runtime-loader.ts` 改成按配置选适配器。
3. 每搬一批就跑 `npm run typecheck` 和 `npm test`，与 B 的基线对比。**一个提交只做一件事**，测试不绿不合入。

**做法（M2，M1 全绿之后）**
1. `launch.ts`、`doctor.ts`、`configure.ts`、`factory.ts`：把"连 Paseo"的部分移进适配器；体检拆成通用和适配器两部分。
2. 运行时层：适配器声明能力，未声明的能力统一返回 `null`，去掉各调用点自己的降级写法。
3. 状态 v2 与迁移函数（见 [state-v2.md](../design/state-v2.md)），迁移要有测试；对外契约保持 `schema: 1`。
4. 平台词汇表先收敛 `messages.ts`、`launch.ts`、`control.ts`；加 CI 检查：核心目录里搜到平台名即失败。

**产出**：搬运后的核心、适配器目录、迁移测试、CI 检查。

**怎么复核**：`npm run typecheck`、`npm test`、`npm run eval:self-check` 与基线一致；`grep` 核心目录搜不到平台名。

**完成标准**：M1 和 M2 的完成标准（[plan.md](plan.md)）。

**注意**：契约（`contracts/agent-runtime.md`）由 C 维护；D、E 提变更需求，不直接改。1.x 的缺陷修复按 [compat-migration §3](../design/compat-migration.md) 登记移植清单。

## D 内部平台适配器（里程碑 M4）

**目标**：在摸高平台上手写第一版适配器，通过一致性测试并跑通一个端到端用例。

**前置**：G0（A 的报告里引擎位置、状态来源、HITL 语义有答案）。

**做法**
1. 把 A 的答案填进 [internal-platform-adapter.md](../design/internal-platform-adapter.md) 的 §2、§3、§6，更新映射表；删掉已被事实否定的推测。
2. 决定 HITL 处理方式（该文档 §4 的方式 A 或 B）。
3. 实现必需能力：`startAgent`、`StepAgent.wait`（轮询状态，映射到 `idle / error / permission / timeout`）、`attachAgent`、`notifyAgent`、`interruptAgent`、`verifyOrigin`；没有的能力按契约降级，不要在适配器里伪造。长提示词用文件传参，凭据只走环境变量。
4. 用 A 的原始输出做**假命令行**脚本重放，写适配器单元测试。
5. 写探针（起任务、查状态、触发并处理一次 HITL），能力矩阵由探针结果生成。
6. 设计平台技能调用方式（版本计划、需求、用例、wiki）：依据 A 的第 4 项实验，走命令行或集成模块，参数放配置。
7. E 的 `runConformance` 可用后接入；挑一个 `evals/` 用例端到端跑。

**产出**：适配器、能力矩阵、探针测试、假命令行夹具、一次端到端运行记录。

**怎么复核**：另一位成员用假命令行跑单元测试；在摸高平台上跑探针，能力矩阵与记录一致。

**完成标准**：[plan.md](plan.md) M4 的完成标准。

**不做**：不用平台动态工作流；不生成适配器（生成在阶段 3）。

## E 一致性测试与无头运行时（里程碑 M3）

**目标**：做出"任何适配器都要通过"的一致性测试套件，以及第二个非 Paseo 适配器。

**做法**
1. 从 `engine/test/pipeline.test.ts` 和 `engine/test/fake-runtime.ts` 抽出编排期望，做成 `runConformance(adapter)`：按 [agent-runtime.md](../../contracts/agent-runtime.md) 的必需、可选、按需三级分别测试，并验证没有能力时的降级行为。
2. 用 Paseo 适配器先验证套件本身：Paseo 必须通过，且套件对故意做坏的假适配器要失败。
3. 实现无头 CLI 运行时：每个步骤 agent 是一个编码 agent 命令行的子进程，`wait` 看进程退出和结果文件，通知写文件或走外部通知器。先用假命令行脚本做测试。
4. 条件允许时用真实的 Pi 或 opencode 命令行跑一个 `evals/` 用例（能否使用以环境为准，待 B 确认）。

**产出**：一致性测试套件、无头运行时、假命令行夹具、一次评估运行记录。

**怎么复核**：套件对 Paseo 通过，对"故意做坏"的适配器失败；无头运行时不依赖 Paseo 即可跑通一个评估用例。

**完成标准**：[plan.md](plan.md) M3 的完成标准，"夸大"为零。

## F 试用场景与对外

**目标**：让摸高试用有可比的口径、可判分的样例，以及团队听得懂的说明。

**做法**
1. **定口径**：和摸高团队确认"20% 端到端交付"的分母（进入流程的需求）、分子（走到哪一步算数：可验收、待测试还是上线）。写成一页，评审通过后不再改。
2. **选范围**：1 个子系统（1 个后端微服务加对应前端），3 到 5 个低风险需求（小改动、缺陷）。
3. **每个需求写成评估用例**，格式沿用 `evals/cases/<名称>/`：`case.json`、已确认的 `spec.md`（验收标准带具体例子）、`hidden/` 隐藏验收、`reference/` 参考实现。
4. **解决一个已知缺口**：现有评估要求隐藏测试"只依赖 Node.js"，而摸高是 Java 微服务加 React、Vue。要么把隐藏验收写成对服务接口的黑盒 Node 测试，要么扩展评估运行器支持别的命令。**这是需要决定的事，先提给小队**，不要默默绕开。
5. 确认需求编号 `CSP-CMASTER#9999` 里的 `#` 怎么规整进目录名（建议规整为 `-`，编号原样保留在需求说明里）。
6. 写试用方案：每步记录什么（用时、token、人工介入次数）、结果文件保留位置、反馈渠道；准备给团队的说明（基于分享稿）。

**产出**：口径页、样例集、试用方案、说明材料。

**怎么复核**：每个样例都能用参考实现通过隐藏验收（`npm run eval:self-check` 同类检查）；口径页经摸高团队书面确认。

**完成标准**：G2 的判断标准在试用开始前已写定。
