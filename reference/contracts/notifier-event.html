外部通知事件（notifier） ​

流水线除了把消息发回发起的对话，还可以在关键时刻调用本机的通知模块，例如把消息转发到企业内部 IM。req-kit 只定义调用方式和事件格式，不包含任何 IM 的实现；模板见 notifiers/im-template.mjs。

配置 ​

只能写在本机配置（~/.req-kit/config.json）或团队配置中，项目配置中的 notifiers 会被忽略（项目仓库里的代码不应该决定往哪里发消息）。

json
"notifiers": [
  {
    "module": "~/.req-kit/notifiers/im.mjs",
    "events": ["blocked", "failed", "completed"],
    "options": { "webhook": "https://im.example.internal/hook/xxx", "tokenEnv": "IM_TOKEN" }
  }
]
字段说明
module通知模块的路径。相对路径相对于声明它的配置文件；~/ 表示用户目录。
events要接收的事件类型，省略时接收全部（包括以后新增的类型）。
options原样传给模块的第二个参数。密钥不要直接写在这里，写环境变量的名字，由模块读取。

模块 ​

ES 模块，默认导出（或导出名为 notify 的）函数：

js
export default async function notify(event, options) { /* 发送 */ }
  • 每个事件调用一次，可以返回 Promise。超过 15 秒没有完成按失败处理。
  • 抛出的错误和超时只记入流水线日志（"外部通知失败……不影响流水线"），不会让流水线停下或重试。
  • 模块在一次流水线运行中只加载一次；修改模块后，对之后启动或继续的流水线生效。
  • 测试：req notify-test [--type blocked|failed|completed|milestone|permission|phase_done|approval|digest|alert] 发一条带"【测试】"字样的示例事件，不需要运行流水线。

事件格式（schema 1） ​

json
{
  "schema": 1,
  "type": "blocked",
  "at": "2026-10-13T08:30:00.000Z",
  "kitVersion": "1.3.0-beta.1",
  "feature": { "dir": "docs/features/20261012-sms-login", "name": "20261012-sms-login", "title": "短信验证码登录" },
  "repo": "D:\\work\\shop",
  "branch": "feature/20261012-sms-login",
  "profile": "standard",
  "originAgentId": "agent-id 或 null",
  "text": "方案审核发现 1 个需要需求方决定的问题，流水线已暂停，请到发起的对话中回答。",
  "details": { "questions": ["……"], "resumeCommand": "node \"…/start-pipeline.mjs\" … --resume" }
}

text 是一两句可以直接发出的话；需要自己排版时用 details。

laoshi M2c 起（ADR 0007）另有两个字段：codebase（需求所属的代码库 { root, remote }，见 cli-json.md；本机的 alert 没有对应仓库时为 null）和 user（为谁运行，取法见 usage-record.md）。只加字段，schema 仍为 1。

发给谁（1.12 起，people）：

json
"people": {
  "audience": "requester",
  "requester": "张广祥",
  "card": { "system": "ALM", "id": "CMASTER-BUSINESS#9902", "url": null },
  "recipients": [{ "name": "张广祥", "accounts": { "um": "ZHANGGX001" } }]
}
  • audience：requester 表示这件事要需求方处理或是给他的结果（blocked、approval、phase_done、completed，而且需求从卡片开始、知道提出人）；其余为 team，发到群里即可。
  • requester、card：从卡片开始的需求的提出人和卡片；其他需求为 null。
  • recipients：audience 为 requester 时是需求方本人；accounts 来自本机或团队配置的 people（姓名 → 各种账号），没有写时为 {}，模块可以改发到群。
type什么时候details
milestone方案确定、开始验证、开始修复缺陷（配置 notifyMilestones 为 true 时，每次尝试各一次）milestone：design-settled、code-reviewed、fixing-defects、handback-<n>（1.7.0 起，测试验证第 n 次把缺陷退回研发）
blocked方案审核发现需要需求方决定的问题，流水线已暂停questions（字符串数组）、resumeCommand
permission步骤 agent 在等待权限批准stepTitle、agentTitle、requests（字符串数组）
failed流水线因错误中断（已自动重试过的临时错误除外）stepTitle、reason、logPath、resumeCommand
completed流水线结束，报告已生成outcome（completed、completed_with_issues、not_completed）、summary、reportPath。"只做研发"时另有 mode（develop-only）和 handoffPath，报告是研发报告，需要人工测试
approval1.8.0 起。方案确认点（designApproval）：方案已通过审核，等待需求方确认"做完后会看到什么"，还没有开始写代码previewPath（要确认的内容）、approveCommand（确认后继续的命令）、resumeCommand（修改需求后继续的命令），都在发起的对话中执行
phase_done1.7.0 起。分阶段执行时研发阶段已完成（代码已通过评审、提测说明已写好），流水线停在闸口等待测试验证。测试退回后再次修完也会发handoffPath（提测说明）、mode（gated）、verifyCommand（开始测试验证的命令，在发起的对话中执行）、verifyAt（预约的开始时间，ISO 格式，没有为 null）、handbacks（已退回的次数）
alert1.12 起。接单器（req factory）自检没有通过（平台连不上、agent 没有登录、额度用完、需求管理系统的命令不可用），暂停接新卡片；或者恢复正常。同样的问题只发一次。feature.title 为"接单器"，feature.dir、repo 为空source（factory）、machine、problems（字符串数组，恢复时为空）、recovered。1.14 起，步骤 agent 运行或开始运行危险命令（dangerGuard）时也发：details.kind 为 danger，另有 stepTitle、command、label、ran；这时 feature、repo 是那个需求的
digestreq digest --notify（或由 req digest --schedule 创建的平台定时任务）发送项目的需求总览，1.6.0 起。feature.title 为"<项目> 需求总览"，text 是完整的多行总览features：每个需求的 name、title、stage、branch、updatedAt、usage；recurringLessons（1.8.0 起）：在两个以上需求的 lessons.tsv 中出现的问题类别，每项 category、features、rules

兼容性 ​

  • 同一 schema 内只增加字段，不删除、不改含义；模块应忽略不认识的字段和事件类型。
  • 不兼容的变化会提升 schema，并在 CHANGELOG.md 的"升级须知"中说明。
